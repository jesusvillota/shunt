## Question and options

Two linked choices for the driver and the provider.

1. **Driver form.** (a) Rust inside shunt; (b) a small helper process (Node or Bun) per account, behind a stable JSON protocol owned by shunt, started and stopped by shunt like agy; (c) reuse the repo's daemon as a sidecar (not recommended: it wants to own Codex's config and has only normal + DEV profiles).
2. **Provider name.** The goal tool already has a worker platform `chatgptweb` (dispatch to ChatGPT Web that opens a PR through the GitHub connector). Keep `chatgptweb` for the provider anyway, or use a clearer name such as `chatgptweb_browser`?

The owner said for (1): choose what is better long term. Criteria: how fast the driver can be fixed when ChatGPT changes its page; testability without a browser; packaging and runtime dependencies; reuse of MIT code from the repo; clean separation from shunt's core.

## Evidence

TASK-001's report (sections `Driver mechanics`, `Shunt seams`, license notes and name options). Shunt's handling of external agent processes: `src/shutdown.rs`, `src/adapters/antigravity`.

## Recommendation

Planner lean: **(1b) helper process behind a stable protocol that shunt owns**, with TASK-002's fake driver keeping shunt tests free of any browser. The web page changes often, so the part most likely to need fast fixes should be replaceable without rebuilding shunt, and the repo's MIT code can be reused. Cost: a runtime dependency to document. **(2)** a distinct name (`chatgptweb_browser` or similar) to avoid confusion with the goal tool's worker platform. Revisit if TASK-001 finds a good Rust browser-control path. The owner decides.
